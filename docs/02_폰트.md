# 심슨 히트 앤 런 (GC) — 폰트 조사

세션 2 · 2026-09-08 · **✅ 폰트 발견·포맷 해독.** 세션 1 의 최대 관문 해소.

## 1. ★★★ 폰트는 UI p3d 안에 «인라인» 이었다

세션 1 에서 「FST 에 `fonts/` 디렉터리가 없다」로 막혔었다. 답은 후보 ② 였다 —
`fontX_YY.p3d` 는 참조 청크(`0x00018104`)에 적힌 **제작 시점 경로**일 뿐이고,
실물은 각 UI p3d 파일 «안에» 청크로 들어 있다. 별도 파일이 아니다.

```
0x00022000  FONT      폰트 머리
  0x00019000  TEXTURE   "<이름>_texture_0"
    0x00019001  IMGHDR
      0x00019002  IMGDATA   ← PNG 원본 (4bpp 팔레트 + 알파)
  0x00022001  GLYPHS    글리프표
```

## 2. 폰트 5종 · 어디에 몇 벌 있나

| 폰트 | 크기 | 아틀라스 | 들어 있는 p3d |
|---|---:|---|---|
| `boulder_16` | 16 | 256×128 | backend · bootup · language · frontend · ingame **(5벌)** |
| `boulder_24` | 24 | 256×256 | frontend · ingame |
| `Tt2001m__14` | 12 | 256×128 | bootup · language · frontend · ingame |
| `swz721mi_12` | 12 | 256×128 | frontend · ingame |
| `swz721n_10` | 10 | 256×64 | frontend |

전부 **136 글리프** — 기본자 U+0000(□ 대체) + ASCII 0x20~0x7E(95) + 라틴 확장 39
(`¡ ¥ § © ® µ º ¿ Á Ä É Ê Í Ñ Ó Ö Ú Ü ß à á â ä ç è é ê í î ï ñ ó ô ö ú û ü Œ œ`) + U+7F7F(□).

⚠️ **같은 폰트가 파일마다 복제돼 있다.** 한글을 넣으려면 «전 사본»을 다 고쳐야 한다.
(텍스처 이름이 폰트 이름과 안 맞는 경우도 있다 — `Tt2001m__14` → `UNIVER01_12_texture_0`,
 `swz721n_10` → `Tt2001m__10_texture_0`. 제작 과정의 잔재로 보인다.)

## 3. 청크 배치 — 실측 확정

### `0x00022000` FONT (데이터 38 B)

```
u32   version = 0
u8    len = 12
char  name[len]        NUL 패딩 ("boulder_16\0\0")
u8    ? = 0            ★ 이름 필드 뒤에 1바이트가 더 있다 (안 세면 float 이 밀린다)
f32   크기             16 / 12 / 10 / 24 / 12
f32   ?                16 / 16 /  9 / 24 / 13
f32   높이             19 / 13 / 13 / 28 / 15
f32   베이스라인       15 / 11 / 11 / 22 / 12
u32   텍스처 수 = 1
```

### `0x00022001` GLYPHS

```
u32   개수 n (=136)
n × 40 B:
   +0   u32  텍스처 번호      (전부 0)
   +4   f32  u0
   +8   f32  v0
   +12  f32  u1
   +16  f32  v1
   +20  f32  좌 베어링
   +24  f32  우 베어링
   +28  f32  폭
   +32  f32  전진
   +36  u32  ★ 문자 코드
```

★ **항등식 `전진 = 좌베어링 + 폭 + 우베어링`** — frontend.p3d 680 항목 전부에서 성립.
★ **문자 코드는 오름차순 정렬**이다(엔진이 이진 탐색할 가능성이 높다).
★ UV 는 0~1 정규화. `boulder_16` 첫 줄 v=0.8438~0.9922 → 128px 기준 y=108~127,
  즉 **아틀라스는 아래에서 위로** 채워진다. u0 최소 0.0039 = 1px → 1px 여백.

## 4. ★★★ 한글이 들어갈 수 있다 — 근거

1. **문자 코드가 u32** 이고 실제로 0xFF 를 넘는 값이 이미 쓰인다(U+0152 `Œ`, U+0153 `œ`).
   바이트 제한 구조가 아니다.
2. 본문 텍스트가 **이미 UTF-16LE** 다(`docs/01` §2). 인코딩 개조가 필요 없다.
3. 아틀라스가 **고정 격자가 아니라 가변폭 패킹**이다. UV 만 맞추면 자유롭게 배치할 수 있다.

## 5. 글리프 예산 — 「완성형 2,350자」가 아니다

필요한 것은 **번역문에 실제로 나오는 음절 종류**뿐이다.

```
영문 원문   1,629 항목 · 61,991자 · 10,821 낱말
길이        평균 38자 · 중앙 23 · 90% 91 · 최대 228
```

62,000자 영문 → 한국어 3~4만 음절 → 음절 «종류» 는 통상 900~1,300.
**상한 어림 1,200자**로 잡으면 1024×1024 한 장에 전부 들어간다.

| 폰트 | 칸(대략) | 1024×1024 수용량 | 1,200자 |
|---|---|---:|---|
| `swz721n_10` | 10×13 | ~7,800 | ✅ |
| `Tt2001m__14`·`swz721mi_12` | 12×15 | ~5,600 | ✅ |
| `boulder_16` | 16×19 | ~3,400 | ✅ |
| `boulder_24` | 24×28 | ~1,500 | ✅ |

→ **다중 텍스처 지원 여부를 증명할 필요가 없어진다**(그게 원래 최대 난제였다).
→ 최종 집합은 번역이 끝난 뒤 실제 코퍼스에서 뽑는다. 다만 **번역을 다 하고 나서
  「글리프가 안 들어간다」가 되면 늦으므로**, 초벌 수백 줄로 음절 종류 증가 곡선을 먼저 본다.

## 6. 남은 관문

1. 엔진이 **136 개보다 많은 글리프**를 다루는가 (개수가 어딘가 박혀 있지 않은가)
2. GC 가 **1024×1024 텍스처**를 받는가 · PNG 를 런타임에 푸는가
3. **어느 폰트가 자막·미션문에 쓰이는가** — 한글 넣을 폰트를 줄이면 작업량이 준다
4. **ISO 재빌드에서 파일 크기 변경이 되는가** (아틀라스가 커지면 p3d 가 커진다)

★ 1·2 는 PoC 한 번으로 같이 판정된다 — 한글 몇 자를 `boulder_16` 에 끼워 화면에 띄워 본다.
  단 PoC 에도 ISO 재빌드가 필요하므로 **4번을 먼저** 봐야 한다.

## 8. ✅ 한글 글리프 구움 (2026-09-08) — `tools/kfont.py`

### 자막이 쓰는 폰트를 먼저 확정했다

레터박스의 세 텍스트 요소(`Skip`·`Cancel`·`Accept`)는 꼬리에 폰트 이름을 평문으로 달고 있다:

```
... 08 "font0_16" ...      ← 제작 시점 이름. 실물은 ingame.p3d 안의 boulder_16
```

⇒ **자막 폰트 = `boulder_16`** (아틀라스 256×128, 박스 높이 19).

### 아틀라스 규약 (실측·재현 확인)

```
PNG P모드 4bpp · 팔레트 16칸이 «전부 흰색» · 투명도는 tRNS 의 16단계 램프(0x00,0x11,…,0xFF)
⇒ 실질 «알파 전용» 폰트. 색인 = 알파 단계.
글리프는 높이가 전부 같은 고정 박스(19px), 폭만 가변. UV 폭 × 텍스처 폭 = 픽셀 폭.
```

### 결과

```
기존 136 글리프를 원본 아틀라스에서 «픽셀 그대로» 오려 보존
+ KS X 1001 완성형 2,350자 (NanumGothicBold 15px, 베이스라인 15)
= 2,486 글리프 · 1024×1024 중 세로 721px 사용 (70.4%)

work/font/kr_boulder_16.png        새 아틀라스
work/font/kr_boulder_16.glyphs     새 글리프표 (2,486 × 40B + 머리 4B = 99,444 B)
work/font/kr_boulder_16_preview.png
```

★ 「1,200자면 충분」이라 봤지만 **2,350자 전량이 여유롭게 들어간다**(70%). 예산 논쟁이 사라졌다.

### ★★★ 한 줄에 들어가는 한글 = 29자

```
영문 자당 평균 전진   8.1 px
한 줄 예산            441 px   (실증된 영문 55자 기준)
한글 전진             15 px 고정
→ 한 줄 29자 · 자막 한 장(두 줄) = 58자
```

예시 `마지: 호미, 집에 있던 디저트를 누가 다 먹어치웠어.` (30자) = 350 px — 한 줄에 들어간다.

⚠️ 영문은 두 줄 110자였는데 한글은 58자다. 원문 98자를 한글 58자에 담아야 하므로
**압축이 필수**다([[feedback_subtitle_unit_is_audio_start_not_script_line]] 와 겹쳐 작용한다).
더 필요하면 렌더 크기를 13px 로 낮춰 한 줄 34자까지 늘릴 수 있다(가독성과 맞바꿈).

## 9. 한글 주입 실전 — 실기에서 밟은 함정 전부 (2026-09-08)

### ⛔⛔ (1) UV 의 v 는 «아래에서» 잰다

가장 크게 헤맨 것. 원본 첫 글리프 `v0=0.8438 v1=0.9922`(H=128)를 «위에서» 재면 행 108~127
인데 **잉크는 행 2~19 에 있다.** 아래에서 재면 행 1~20 — 이쪽이 맞다.

이걸 모르고 만들었더니 **영문까지 전부 사라졌다**(빈 영역을 오려 오고, UV 도 빈 곳을 가리킴).
검산법: 다시 구운 아틀라스의 «잉크 픽셀 수»가 원본과 정확히 같아야 한다(9,094 = 9,094).

### ⛔ (2) PNG 는 IDAT 를 «한 덩어리»로

PIL 은 64KB마다 IDAT 를 쪼갠다. 원본은 하나뿐이다. `tools/kfont.py:single_idat()` 로 합친다.
(규격상 여러 IDAT 는 합법이지만 원본과 같은 모양으로 맞추는 게 안전하다.)

### ★★★ (3) 텍스처 크기 상한 — 실측

| 아틀라스 | 디코드 | 결과 |
|---|---:|---|
| 256×128 (원본) · 256×256 | 16·32 KB | ✅ |
| **512×512** | **128 KB** | ✅ |
| 1024×512 | 256 KB | ⛔ 게임화면 진입 직전 크래시 |
| 1024×1024 | 512 KB | ⛔ 같음 |

⇒ **한 장에 13px 한글 약 780자**뿐이라 2,350자는 «다중 텍스처»가 필요하다.
   폰트 머리의 «텍스처 수»와 글리프의 «텍스처 번호»가 있으니 구조는 지원한다
   (`tools/kfont.py --pages`, `tools/p3dinject.py --png a.png b.png`). ⏳실기 미검증.

### ★★★ (4) 글리프 개수 136 초과는 «크래시하지 않는다»

178개로 정상 부팅했다. 다만 «렌더»가 되는지는 별개 문제(아래 §10).

### ★★★ (5) 폰트 사본은 5개가 아니라 «6파일 × 최대 5종»

```
backend · bootup · language · frontend · ingame · minigame   ← minigame 을 빠뜨렸었다
각 파일 안에 boulder_16 / boulder_24 / Tt2001m__14 / swz721mi_12 / swz721n_10
```
⚠️ 요소에 적힌 폰트 이름(`font0_16`)은 **제작 시점 이름이라 실물과 안 맞는다.**
메모리에 폰트 코드배열이 **7벌** 떠 있는 것을 확인했고, `boulder_16` 만 고쳤을 땐
3벌만 한글이었다. ⇒ **전 파일 · 전 폰트를 다 고쳐야 한다.**

### (6) 조판 편집을 날려 먹지 말 것

`ingame.p3d` 에는 지난 세션의 «요소 위치·아이콘 제거» 편집(23바이트 5구간)이 들어 있다.
손 안 댄 `work/extract/ingame.p3d` 로부터 다시 만들면 그게 날아간다.
⇒ 반드시 **`work/extract/ingame_layout.p3d`** 를 바탕으로 주입할 것.

## 10. ⏳ 남은 문제 — 한글이 □ 로 나온다

폰트 7벌 전부에 한글이 들어갔고 자막 칸 주소도 맞는데, 화면엔 □ 와 엉뚱한 `9 D @` 가 섞인다.

읽어낸 조회 경로:
```
0x8023DC64  lhzx r4, r28, r29     ; 문자열에서 «16비트» 로 한 글자
0x8023DC14  bl 0x8023DCE8         ; 조회
0x8023DCE8  r6=[폰트+0x40] u16 코드배열 · r3=[폰트+0x38] 개수
            정렬 배열 이진 탐색, 못 찾으면 -1 → 대체 글리프(□)
```
탐색 자체는 정상이고 배열도 정렬돼 있는데 «배열에 있는 마 조차» 못 찾는다.
⇒ **조회에 넘어가는 값이 우리가 쓴 UTF-16 코드가 아니다.**
   `lhzx` 는 빅엔디안 읽기인데 바이블은 UTF-16 **LE** 다 —
   중간에 «변환된 사본»이 있고 그 변환이 한글을 망가뜨리는 것으로 보인다.
   ⏳ 다음 수순 = RAM 에서 BE/LE 사본을 찾아 어느 버퍼를 그리는지 확정.
