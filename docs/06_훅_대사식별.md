# 정찰 훅 — 「어느 대사인가」를 알아내기

세션 2 · 2026-09-08. 도구 `tools/dolhook.py`(심기) · `tools/spyread.py`(읽기) · `tools/dolmem.py`(돌핀 RAM).

## 1. 심은 것

```
VA 80132520  48002DE9 (bl 0x80135308)  ->  4BED2369 (bl CAVE)

CAVE = 0x80004888   ← text0 의 0 구간 1,228 B (예외벡터 템플릿 슬롯의 꼬리 패딩)
    lis  r12,0x8000
    stw  r4, 0x4A00(r12)   ; 고른 대사 객체
    stw  r30,0x4A04(r12)   ; 이벤트 ID
    lwz  r11,0x4A08(r12) / addi r11,r11,1 / stw r11,0x4A08(r12)   ; 호출 횟수
    stw  r3, 0x4A0C(r12) / stw r5,0x4A10(r12) / stw r31,0x4A14(r12)
    b    0x80135308        ; LR 을 안 건드리므로 원래 자리로 복귀
```

⛔ **`addi r0,r0,1` 을 쓰면 안 된다** — PPC 의 `addi` 는 rA=0 을 「레지스터 r0」이 아니라
«상수 0» 으로 읽어 `li r0,1` 이 된다. 카운터는 r11 로. (캡스톤 역어셈으로 잡았다)

## 2. ★★★ 이 게임은 «MMU 가상 메모리»를 쓴다

훅이 잡은 대사 객체 포인터가 `0x7E13BAD0` — MEM1(`0x80000000~0x81800000`) 밖이다.
그런데 게임은 그걸 `lwz r12,0(r3)` 로 역참조하고도 안 죽는다.

→ 게임이 **게스트 `0x7E000000~0x80000000` 을 MMU 로 매핑해 힙으로 쓴다.**
돌핀은 그 영역을 «fake VMEM» 이라는 **MEM1 과 별개인 32 MB 매핑**으로 흉내낸다.

⚠️ MEM1 뷰로 같은 오프셋을 읽으면 **엉뚱한 «코드»가 나온다**(0x8013BAD0 = text1).
`tools/dolmem.py` 에 `find_vmem()` 을 넣어 구분했다 — 32 MB MEM_MAPPED 구간 중
「그 포인터가 말이 되는 곳」(vtable 범위 + 객체 `+0xC` 가 이벤트 ID 와 일치)을 고른다.

## 3. 대사 객체 구조 (실측)

`0x80132520` 은 **대화 하나에 한 번** 불린다(줄마다가 아니다). 이벤트 0x11F=convinit.

```
vtable 0x8037B430  묶음 노드      vtable 0x8037B36C  줄 노드
  +00 vtable                        +00 vtable
  +04 idxA                          +04 idxA
  +08 idxB                          +08 idxB
  +0C 이벤트 ID (0x11F / 0x124)     +0C 이벤트 ID
  +10 다음 노드                     +10 다음 노드 (또는 0)
  +14 …                             +14 → 리소스 배열
  +18 …                             +18 ★ 주제 해시
  +1C …                             +1C 플래그 (00010100 / 00020000 / 00032300)
```

`+0x14` 가 가리키는 배열은 0x14 B 항목:
`8037F4A4 · 19991999 · <해시표 포인터> · FFFF0201 · 00020000` — 포인터가 4씩 증가한다.
그 해시표(예 `0x808F1340`, `0x808F1880`)는 32비트 해시가 죽 늘어선 표다.

## 4. ★★★ 해시 함수 확정 — `h = 31*h + c` (부호 있는 char)

DOL `0x801341E4` 의 인라인 루프에서 읽었고, RAM 의 해시표가 이를 확증했다:

```
0x808F1880:  … 36452C84  36534405  36615B86 …   차이가 정확히 0x0E1781
0x0E1781 = 923,521 = 31^4     → 이름 «뒤에서 5번째 글자»만 1 다른 이름들
```

그리고 결정적 확인:

```
줄 노드 +0x18 = 0xC26638D7 = h31("icecream")
```

`icecream` 은 **그 대화의 «주제»** — 미션 스크립트 `.mfk` 의
`SetDialogueInfo("화자","상대","주제",0)` 셋째 인수이자, 대사 파일 이름
`c_ <주제> _n_ convinit _ <화자> _ <미션> .rsd` 의 그 자리다.
(실제로 사용자가 멈춰 둔 장면이 아이스크림 대화였다.)

★ 지난 세션에 `0x8044A81C` 를 crc32·djb2·sdbm·fnv 로 맞춰 보고 실패했는데,
**엔진이 쓰는 해시는 이 `*31` 이었다.** 후보 해시를 고를 땐 «게임 자신의 코드»에서 읽을 것.

## 6. ★★★ 줄 단위 훅 확정 — `0x80136430`

데이터 관찰(재생기 0x44 B · 매니저 · 사운드 콜백 · 힙 통짜 diff)로는 「줄 경계」를 못 찾았다.
결국 **재생기 클래스의 코드**를 읽어서 찾았다. vtable `0x8037B224`.

```asm
80135F20  「한 줄 끝 → 다음 줄」
    lwz  r3,0x14(r31)     ; 대화 묶음 노드
    lwz  r12,0x38(r12)    ; → 줄 개수  (r30)
    lwz  r3,0x2c(r31)     ; ★ 현재 줄 색인
    addi r0,r3,1
    cmplw r0,r30
    stw  r0,0x2c(r31)     ; ★★★ 재생기 +0x2C 가 «줄 색인» 이다
    blt  0x80136058       ; 남았으면 → 0x8013609C: lwz r4,0x2c(r31) / bl 0x80136430

80136430(r3=재생기, r4=줄 색인)   ← 「줄 #색인 재생 시작」. 줄마다 한 번.
```

★ 앞선 추적에서 `재생기+0x2C` 가 대화 내내 `0→1` **한 번만** 바뀐 건 버그가 아니라
그 묶음이 짧아서였다 — 값의 «의미»를 모른 채 변화 횟수만 보면 오판한다.

### 심은 훅 (`dolhook.py --apply line`)

```
0x8013643C  93E1003C (stw r31,0x3c(r1))  ->  bl CAVE2
```
★ 함수 첫 명령(`stwu`)이 아니라 **네 번째 명령**을 가로챈다 — 거기선 LR 이 이미
`0x44(r1)` 에 저장돼 있어 `bl` 로 들어가 `blr` 로 나와도 안전하다.

```
CAVE2 = 0x800048C0
    stw  r31,0x3C(r1)     ; 밀어낸 명령
    lis  r12,0x8000
    lwz/addi/stw r11,0x4A20(r12)   ; 호출 횟수
    stw  r3,0x4A24(r12)   ; 재생기
    stw  r4,0x4A28(r12)   ; 줄 색인
    lwz  r0,0x14(r3) / stw r0,0x4A2C(r12)   ; 대화 묶음 노드
    blr
```

### ✅ 실측 (2026-09-08)

```
[ 4.17s] ▶ 줄 #1  색인=1  묶음=7E13BAD0  주제=C26638D7(icecream)
[14.01s] ▶ 줄 #3  색인=2
[16.83s] ▶ 줄 #4  색인=2
```
대사가 바뀔 때만 불린다. 읽개 `tools/linewatch.py`.

⛔ 남은 것: 리소스 배열의 해시(`A863C9C4` 등)가 `dialog.rcf`·`scripts.rcf` 이름과
아직 안 맞는다 — 줄→파일 대응은 더 파야 한다. 다만 **자막 동기에는 필요 없다**
(묶음 노드 + 줄 색인만으로 「몇 번째 줄인지」가 정해진다).

## 8. ✅ 자막 전환 규칙 확정 (2026-09-08)

훅 세 개를 다 걸고서야 «대사 한 장»의 정의가 잡혔다.

| 훅 | 자리 | 밀어낸 명령 | 잡는 것 |
|---|---|---|---|
| `spy` | `0x80132520` | `bl 0x80135308` | 대화 시작(이벤트ID·묶음 노드) |
| `first` | `0x801361FC` | `lwz r4,0x2c(r30)` | **첫 줄(색인 0)** — `0x80136430` 을 안 거친다 |
| `line` | `0x8013643C` | `stw r31,0x3c(r1)` | 줄 넘김(색인 1,2,…) |

⚠️ 둘 다 함수 첫 명령이 아니라 **LR 이 이미 저장된 뒤의 명령**을 가로챈다.
그래야 `bl`/`blr` 로 드나들어도 안전하다.

케이브는 **16칸 고리 버퍼**(`0x80004B00`, 색인+묶음노드)에 이력을 남긴다 —
호스트 폴링이 «같은 순간의 두 호출»을 흘리는 문제를 원천 차단한다(실측 유실 0회).

### ★ 관측된 호출 형태

```
 3.83s  색인 0        ← 마지 시작
 3.83s  색인 1        ← 같은 순간(예약)
13.91s  색인 1        ← 호머 시작
13.92s  색인 2        ← 같은 순간(예약)
17.03s  색인 2        ← 대화 끝
```

경계마다 **두 번** 불린다. 그래서 규칙은:

> **같은 순간(0.25초 이내)에 겹쳐 오는 훅은 첫 것만 쓴다. 그것이 «자막 한 장».**

★ **(2026-09-10 수정) 「같은 순간 + 같은 주제」일 때만 버린다.** 뒤따르는 호출은 «같은 대화의 다음 줄 예약»이므로
주제 해시가 같다. 주제를 안 보던 때는 **다른 대화가 0.26초 안에 이어지면 그 첫 줄을 버렸다** —
L1M7 `talkto` 단계의 `SetCompletionDialog("there")`(번역 없음) 직후 `accuse` 대화가 곧바로 시작돼
첫 줄 「J'accused!」가 버려지고, 레이스 전에 끝난 `adventure` 대화의 마지막 자막이 그대로 보였다.
전 미션 `.mfk` 전수: 완료대사 38곳 중 «바로 다음 단계가 대화»인 곳은 이 한 곳뿐.
노드 주소가 아니라 주제로 가르는 이유 — 해제된 노드 자리에 새 노드가 같은 주소로 올 수 있다.
구현: `ST_LTOPIC = 0x80004A3C`, 케이브4 는 주제를 먼저 읽고 겹침을 판정한다(103워드).

✅ 화면 확인 완료 — 마지 3.83초, 호머 13.91초. 사용자 판정 「완벽해」.

### ⚠️ 이 규칙이 번역 분량에 거는 제약

★★★ **한 대사가 여러 클립으로 쪼개져 있어도 그 사이 전환은 훅에 안 잡힌다.**
마지의 두 문장(색인 0·1)은 붙여서 재생되고 경계 이벤트가 없다.
⇒ **번역 단위는 「원문 한 줄」이 아니라 「음성 시작 하나」다.**
   마지의 두 문장은 자막 한 장(두 줄 · 각 55자)에 **압축**해 넣어야 한다.

```
Marge: Homie, somebody ate every dessert in the house. Get me that ice cream with the little pies.
```
(원문 139자 → 98자로 압축해 두 줄에 맞췄다)

## 9. 케이브 이식 완료 (2026-09-08) — 호스트 없이 게임 혼자 자막을 띄운다

`tools/dolhook.py --apply sub` · 케이브 `CAVE4 = 0x80004940` (36명령 144B)

```asm
lis  r12,0x8000
lis  r10,0x8045 / lwz r10,-0x57E4(r10)   ; 지금 = [0x8044A81C] 타임베이스(약 40.5MHz)
lwz  r0,0x4A44(r12) / subf r0,r0,r10     ; 지금 - 마지막표시
lis  r11,0x00A0 / cmplw / blt 끝         ; 0.259초 안에 겹쳐 오면 무시
stw  r10,0x4A44(r12)                     ; 마지막표시 = 지금
lwz  r0,0x4A28(r12) / clrlwi r0,r0,31    ; ★ 줄 색인으로 고른다(무상태)
mulli r0,r0,0xC0 / add r10,r12,r0 / addi r10,r10,0x4B80
→ L1 에 0x60 B 복사, L2 에 0x60 B 복사 / blr
```
⛔ r3·r4 는 안 건드린다(두 훅 자리 모두 인수가 살아 있다). r0·r8~r12·CTR·CR0 만 쓴다.
⛔ 전역 카운터 홀짝으로 고르면 **다른 대사가 먼저 훅을 건드리면 순서가 뒤집힌다** — 실제로 겪었다.

✅ 실기 결과: **타이밍 완벽**(사용자 확인). 호스트 프로그램 없이 대사에 맞춰 자막이 넘어간다.

## 10. ⚠️⚠️ 자막 칸 주소는 «파일 크기를 바꾸면 밀린다»

텍스트 바이블 블롭은 힙에 올라가므로 p3d 파일 크기가 바뀔 때마다 시작 주소가 이동한다.
실측 이동 예: `0x808BC919 → 0x808C1001 → 0x808BFC79 → 0x808C3C79`.

측정 도구 `tools/rebase.py` — **자막 칸을 기준으로 삼으면 안 된다**(케이브가 덮어쓰면 사라진다).
절대 안 건드리는 문자열을 기준으로 역산한다.

```
기준 'Unable to load The Simpsons Hit & Run saved game.'  블롭 +0x598
자막 칸 블롭 오프셋:  윗줄 +0x06B4E ("Start Mission") · 아랫줄 +0x02B80 ("Cancel")
```

⚠️ 실행 중 RAM 패치는 **케이브가 아직 한 번도 안 돌았을 때만** 먹는다
   (돌핀 JIT 이 이미 컴파일했으면 호스트가 쓴 코드 변경이 반영되지 않는다.
    `0x80004A48` 표시 횟수가 0 이어야 한다).

⛔ **배포판은 이렇게 박으면 안 된다** — 블롭 포인터를 런타임에 얻는 방법이 필요하다.
